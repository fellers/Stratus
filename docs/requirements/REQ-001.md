# 1. Purpose

This document defines the organization, ownership, and structure of the Stratus Rev A requirements package.

The requirements package establishes the engineering baseline from which system architecture, implementation, verification, and validation activities are derived.

Detailed requirements are maintained in subsystem-level requirements documents. This master document serves as the authoritative index for those specifications and defines the conventions used across the requirements package.

All requirements shall be uniquely identified to support traceability throughout the project lifecycle.

---

# 2. Scope

This document applies to Stratus Rev A and covers the requirement categories necessary to establish the initial autonomous aerial robotics platform.

The requirements package supports the objectives defined in **SPEC-001** and provides the basis for:

- System architecture
- Hardware selection and integration
- Embedded software implementation
- Mechanical design
- Electrical design
- Documentation
- Verification
- Validation
- Future system revisions

Requirements contained in subsystem-level requirement documents shall be treated as applicable to Stratus Rev A unless explicitly marked as:

- Planned
- Deferred
- Superseded
- Deprecated
- Not applicable

## 3.3 Document Identifier Format

Requirements documents shall use the following identifier format:

```text
REQ-<DOMAIN>-<DOCUMENT NUMBER>
```

Examples:

```text
REQ-FR-001
REQ-HW-001
REQ-SW-001
REQ-ME-001
REQ-EL-001
```

## 3.4 Requirement Statement Identifier Format

Individual requirement statements shall use a stable domain or subsystem prefix followed by a sequence number.

Examples:

```text
REQ-FC-001
REQ-SE-001
REQ-MO-001
REQ-COM-001
REQ-HW-001
REQ-SW-001
REQ-ME-001
REQ-EL-001
```

Requirement identifiers shall not be reused after a requirement is removed or superseded.

Where a requirements document and its first requirement currently share the same visible identifier, the document title and context distinguish the document from the individual requirement. A future documentation-normalization pass may introduce a separate document-number namespace if needed.

## 3.5 Requirement Writing Rules

All Stratus requirements shall follow these rules:

1. Each requirement shall describe one required capability, behavior, interface, or constraint.
2. Each requirement shall be independently understandable where practical.
3. Mandatory requirements shall use the word **shall**.
4. Recommended but nonmandatory provisions may use **should**.
5. Requirements shall be objectively verifiable.
6. Requirements shall avoid vague terms such as “fast,” “sufficient,” or “reliable” unless the applicable acceptance criteria are defined.
7. Requirements shall describe what is required rather than unnecessarily prescribing implementation.
8. An implementation choice may be specified when that choice is an approved project constraint.
9. Each requirement shall identify or imply an appropriate verification method.
10. Requirements shall be traceable to upstream objectives and downstream design, implementation, or verification artifacts.
11. Requirements shall not silently conflict with approved architecture or engineering standards.
12. Deferred or future requirements shall be explicitly identified.

# 4. Functional Requirements

Functional requirements define the required behavior and capabilities of Stratus Rev A.

| Document | Subsystem | Status | Description |
| --- | --- | --- | --- |
| [REQ-FR-001](flight-functions/FlightControl.md) | Flight Control | Active | Closed-loop stabilization, control calculations, limits, and control health |
| [REQ-FR-002](flight-functions/StateEstimation.md) | State Estimation | Active | Sensor processing, attitude estimation, timing, calibration, and estimator validity |
| [REQ-FR-003](flight-functions/MotorOutput.md) | Motor Output | Active | Motor mixing, output constraints, arming behavior, and ESC command generation |
| [REQ-FR-004](flight-functions/Communications.md) | Communications | Active | Programming, debugging, diagnostics, telemetry, command reception, and message handling |

## 4.1 Functional Boundaries

The functional requirements are divided so that:

- Flight Control consumes valid state estimates and produces control outputs.
- State Estimation consumes validated sensor measurements and produces aircraft-state estimates.
- Motor Output converts control outputs into safe individual motor commands.
- Communications exchanges diagnostic, telemetry, configuration, and command information with external systems.

No external communications path shall bypass System Supervision, arming logic, or Motor Output safety constraints.

# 10. Requirement Status

Each requirement or requirements document shall use one of the following status classifications where status tracking is needed:

| Status | Meaning |
| --- | --- |
| Draft | Under development and not yet baselined |
| Active | Applicable to the current revision |
| Planned | Intended but not yet fully defined |
| Deferred | Valid but postponed to a later milestone or revision |
| Superseded | Replaced by a newer requirement or decision |
| Deprecated | Retained for history but no longer intended for use |
| Verified | Objective evidence demonstrates compliance |
| Failed | Verification has demonstrated noncompliance |
| Not Applicable | Determined not to apply to the referenced configuration |

A requirements document marked **Active** may still contain individual future or deferred requirements.

# 11. Verification Methods

Each requirement shall be verified using one or more of the following methods:

| Method | Description |
| --- | --- |
| Inspection | Examination of hardware, software, documentation, configuration, or workmanship |
| Analysis | Mathematical, engineering, timing, structural, electrical, or logical evaluation |
| Demonstration | Observation of required behavior without extensive instrumentation |
| Test | Controlled and repeatable execution with objective acceptance criteria and recorded results |

## 11.1 Verification Selection

The selected verification method shall be appropriate to the requirement.

Examples include:

- Component identity through inspection
- Current capacity through analysis and test
- Software dependency direction through inspection
- Timing performance through measurement
- Motor safe-state behavior through oscilloscope or logic-analyzer test
- Mechanical serviceability through demonstration
- Link integrity through automated repository scanning

## 11.2 Verification Evidence

Verification evidence should identify:

- Requirement identifier
- Tested configuration
- Method
- Procedure or reference
- Date
- Result
- Evidence location
- Open anomalies

# 12. Traceability

The Requirements Traceability Matrix shall connect applicable requirements to:

- Upstream objectives in **SPEC-001**
- Architecture elements in **ARC-001**
- Engineering standards
- ADRs and HDRs
- Hardware components
- Software modules
- CAD or electrical artifacts

- Verification results

Traceability may be introduced incrementally as implementation and test artifacts are created.

A requirement shall not be marked verified without identifiable supporting evidence.

---

# 13. Change Control

Changes to requirements shall be managed through version control.

A material requirement change should include:

1. Updated requirement text
2. Updated revision history
3. Review of affected architecture
4. Review of affected decisions
5. Review of affected implementation
6. Review of affected verification artifacts
7. Updated traceability

Requirement identifiers shall not be silently reassigned to unrelated requirements.

Removed requirements should remain identifiable through repository history or an explicit superseded or deprecated status.
